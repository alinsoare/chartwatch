## Context

See `proposal.md` - Why. Today `web/reports/app.js` wires a `#screener-btn` click listener that calls `fetchScreenerData()` (in `screener.js`), persists the result via `saveScreenerBundle()`, and rebuilds the dashboard; the button is enabled only once a report exists and is disabled while the fetch is in flight. `screener.js`'s scoring/resolution helpers (`resolveTicker`, `screenerStatusForTicker`, `attachScreenerToLadders`) are pure and already independent of the button — only the trigger and the fetch/persist orchestration in `app.js` are button-shaped. The two triggers this change needs instead — `boot()` restoring a cached report, and `handleImport()` completing a new import — already exist in `app.js` as the places that currently just enable the button. See `specs/ladder-projection/spec.md` and `specs/report-dashboard/spec.md` for the exact behavior contract this design implements.

## Goals / Non-Goals

**Goals:**
- Replace the button-triggered fetch with the same fetch invoked automatically from `boot()` on every page load — unconditionally, whether or not a cached report is restored — and from `handleImport()` after every successful import, with no other change to what is fetched or how it is scored/rendered.
- Guarantee at most one in-flight screener/catalog fetch at a time, with any additional trigger (including a manual retry) observing the existing in-flight promise rather than starting a second request.
- Give a failed automatic check a visible, dismissible failure notice with a manual retry action, since the button — which doubled as a retry control — is gone.

**Non-Goals:**
- No periodic/polling re-check, no re-check on filter or tab changes, no re-check driven by a settings change (see Decisions below for why settings don't need this).
- No change to `screener.js`'s scoring, ticker-resolution, or staleness logic, nor to the shapes of `data/screener-scores.json` / `data/catalog.json`.
- No change to chart-page (`web/index.html` / main `app.js`) market-data sync, which remains button-only and out of scope.

## Decisions

**A single `ensureScreenerChecked()` orchestrator, not two independent call sites.** Both triggers (boot-restore, post-import) end up wanting "fetch unless one is already running, then persist and rebuild." Centralizing that in one `async function` holding a module-level in-flight promise (e.g. `let screenerCheckInFlight = null;`) means boot, import, and retry all call the same function and naturally dedupe: if `screenerCheckInFlight` is set, await it instead of calling `fetchScreenerData()` again. This directly satisfies the "overlapping triggers" scenario without a separate lock abstraction.

**Alternative considered:** a boolean `isChecking` flag with early-return (drop the second trigger's request instead of joining it). Rejected because a trigger landing mid-fetch (e.g. import finishing while the boot check for the *previous* cached report is still resolving) should still end up reflecting the fetch's outcome once it settles, rather than silently doing nothing and leaving that caller's subsequent render decision stale. Awaiting the shared promise gives every caller the same resolved/rejected outcome with one line of code.

**Failure surfaces through the existing notice pattern, not a new modal.** `render.js` already has `ui.showStorageNotice(...)` / `ui.showError(...)` for comparable non-blocking failure states (storage denied, import parse error). The screener-failure notice reuses that same dismissible-banner pattern with one addition: a retry button wired to call `ensureScreenerChecked({ force: true })`. `force` bypasses "already have a cached bundle, nothing to do" short-circuiting (there isn't one — every trigger always fetches) but is still subject to the in-flight guard, per the spec's "Retry reuses the in-flight guard" scenario.

**Settings changes do not need to re-trigger a fetch.** `screenerStatusForTicker()` in `screener.js` computes staleness and resolution at render time from the already-fetched payload plus the live `settings` object (`settings.screenerStaleHours`, `settings.suffixAliasTable`). `rebuild()` already re-runs this on every render, including the "settings change applies to a cached report" scenario `report-dashboard` already specifies. So a settings edit changes how the *existing* cached payload is interpreted on the next render, with no new network fetch required — this was already true before this change and stays true after it.

**Fetch on the empty state too, so the data is ready for the next import.** `boot()` calls `ensureScreenerChecked()` unconditionally, before the `if (!cached?.report) return;` early-return — not only in the else-path that restores a cached report. This is a deliberate change from the project's usual offline-first default, decided explicitly for this control: the screener is always fetched on load, whether or not a report is cached. `rebuild()` only applies `screenerBundle` to ladders when `parsed` is set (`attachScreenerToLadders` runs inside the `if (!parsed)` guard in `app.js`), so an empty-state fetch has nothing to render against yet — but `saveScreenerBundle()` persists the result via `cache.js` independently of whether a report exists (`saveScreenerBundle` writes `{ report: existing.report ?? null, screener: bundle }`), so the fetched/cached payload is sitting ready the moment a report is imported or restored on a later load, with no second fetch needed to "catch up." Because `handleImport()` always calls `ensureScreenerChecked()` too, in the common case where an import follows shortly after an empty-state load, the boot-time fetch and the import-time fetch are two calls to the same orchestrator: if the boot fetch is still in flight when import completes, the import call joins it via the existing in-flight guard (per the "Overlapping triggers" scenario); if the boot fetch has already resolved, the import call starts its own fresh fetch per the decision that every trigger always fetches (there is no "already have a bundle, skip" short-circuit, as noted below).

## Risks / Trade-offs

- **[Risk] An automatic fetch on every page load (not just when a report is cached) increases default network calls over the prior button-only behavior, including on an empty page with nothing to show yet.** → Mitigation: this is the explicit, accepted intent of the proposal (see the "Project convention note" in `proposal.md` — Impact) and is scoped tightly to this page's two triggers (load, import); it does not touch chart-page sync or introduce polling, and the empty-state fetch's result is cached and reused rather than wasted.
- **[Risk] A user on a flaky connection now sees a failure notice on every load instead of a quiet, never-attempted state.** → Mitigation: failure keeps previously cached confirmation visible (spec requirement, unchanged from today) and the notice is dismissible; the user is never blocked from reading the dashboard.
- **[Risk] Removing `screenerBtn.disabled` bookkeeping could leave dead references if `index.html`/`app.js` edits are incomplete.** → Mitigation: tasks.md enumerates every file touching `screener-btn`/`screenerBtn` found during research (`index.html`, `app.js`); no occurrences were found in `render.js`, `reports.css`, or `cache.js` beyond what's listed.
- **[Risk] This reverses `ladder-projection`'s prior "never on page load, on import, or periodically" rule, which the project's `openspec/config.yaml` offline-first context calls out by name (originally written with the chart page's market-data sync in mind, but phrased broadly enough to cover this control too; a prior archived change, `remove-periodic-refresh`, shows the project has enforced that line strictly before).** → Decided: the reports-page screener check (static same-origin JSON, not live market data) is now always fetched on load and import, as a scoped exception limited to this one control. Chart-page market-data sync is unaffected and stays button-only. `tasks.md` makes updating `config.yaml`'s context note to state this exception explicitly a definite task, not an open question.
